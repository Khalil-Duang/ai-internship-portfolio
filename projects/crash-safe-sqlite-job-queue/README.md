# Crash-Safe SQLite Job Queue

## 案例定位

这是一个 AI Coding / Software Engineering benchmark 设计案例。目标不是只写一个“能跑”的队列，而是把可靠性要求转换成可重复、可评分、能够暴露典型错误的工程任务。

为遵守平台项目保密要求，本仓库不包含原始题面、隐藏测试、内部评分资产或运行轨迹；以下内容为脱敏后的能力案例。

## 我要解决的问题

离线批处理任务由多个 worker 从同一个 SQLite 数据库领取执行。实际系统会遇到：

- 多个 worker 同时争抢同一条任务；
- worker 在持有任务时被强制终止；
- 旧租约尚未释放，新 worker 已经重新领取；
- 同一任务完成后重复写入业务副作用；
- 任务失败后需要指数退避，达到上限进入 dead letter；
- 旧版本数据库需要在保留数据的前提下安全迁移；
- 收到 SIGTERM / SIGINT 时需要停止领取并释放未完成任务。

## 我设计的能力边界

| 维度 | 需要验证的行为 |
| --- | --- |
| 入队幂等 | 相同幂等键重复入队只产生一条任务，并返回同一个 ID |
| 原子领取 | 多 worker 并发领取时，一条任务不会在同一租约中被重复持有 |
| 租约回收 | 租约到期后任务可被重新领取，尝试次数递增 |
| Fencing | 旧 worker 即使拥有旧 lease_id，也不能完成或改变新租约中的任务 |
| 重试策略 | 失败后按指数退避，达到上限转为 dead，并支持人工重新入队 |
| 副作用一致性 | 完成状态与 effects 写入必须处于同一事务，重复完成不能产生重复副作用 |
| 崩溃恢复 | worker 被 kill 后，任务能够被后续 worker 重新领取 |
| 迁移兼容 | 旧 schema 可幂等升级，已有任务不丢失 |
| 优雅退出 | 收到终止信号后停止领取，并释放未完成任务 |

## 测试与评分设计

验证矩阵按风险而不是按代码文件组织，重点关注：

- 8 个并发 worker 的领取竞争；
- 过期租约回收；
- stale holder 完成/失败请求被拒绝；
- 并发 complete 只产生一条 effects 记录；
- 进程被 kill 后的任务恢复；
- 旧数据库迁移和重复初始化；
- CLI 信号处理与退出码；
- 模拟时钟下的重试时间边界。

评审不只检查“正常路径是否成功”，还会用空实现、错误租约和迁移缺陷等失败路径验证测试本身的区分度。

## 我能带走的能力

- 把模糊的“任务队列要可靠”拆成状态机、事务边界和可观察不变量。
- 设计对抗并发、崩溃和边界时间的测试，而不是只验证 happy path。
- 评估一个 Coding Agent 是否真正理解工程约束，而不是只针对可见测试打补丁。
- 用清晰的失败模式解释系统风险，并把修复建议写成可执行任务。

# Near-Duplicate Corpus Audit

## 案例定位

这是一个面向 AI Coding / Software Engineering benchmark 的算法与工程质量案例。它要求参赛代理在离线、纯 CPU 环境中完成近重复语料审计，并输出可独立核验的相似性证据。

为遵守平台项目保密要求，本仓库不包含原始题面、隐藏语料、内部评分资产或模型轨迹；以下内容为脱敏后的案例说明。

## 问题拆解

给定 JSON Lines 语料，需要：

1. 对文本执行明确的规范化；
2. 构造 shingle 集合并计算精确 Jaccard 相似度；
3. 将相似文档组织为图，计算连通分量；
4. 选择最小 `doc_id` 作为簇代表；
5. 对每个簇输出可复核的相似边证据；
6. 对非法输入进行原子失败，不留下半成品输出。

## 技术选择

| 阶段 | 方案 | 设计理由 |
| --- | --- | --- |
| 规范化 | 统一字符与大小写规则 | 降低排版差异造成的假阴性 |
| 候选生成 | 先建立稀疏候选，再做精确复核 | 避免直接做全量两两比较 |
| 相似判断 | 精确 shingle Jaccard | 不把近似召回结果直接当作最终簇 |
| 簇构建 | 并查集 / connected components | 支持桥接边造成的传递合并 |
| 证据输出 | 每簇保留相似边与规范 | 让结果可以由第三方复核 |
| 错误处理 | 输入非法时原子失败 | 避免产生不完整但看似成功的输出 |

## 验证设计

除了正确实现之外，我关注三类具有代表性的错误解：

- **空操作或不可调用**：用于确认基础门槛能够拦截无效提交；
- **传递折叠错误**：只合并直接邻居，漏掉桥接关系；
- **规范化丢失**：漏掉字符或大小写规范化。

这些变体让“功能看起来能跑”和“真正满足契约”之间形成可测分界。

## 结果与证据

- 开发机 CPython 环境中，5,000 文档的基准实现约 0.39 秒完成；
- 正确实现、空操作和两类错误解在同一评分口径下得到明显不同的结果；
- 输出关注簇级证据链，而不是只返回一个无法解释的相似度数字；
- 保留静态环境校验和资源来源记录，便于复现。
